三、实验原理和方法

3.1 Linux 常用操作

Linux 一切皆文件，日常操作围绕“目录树”展开：cd／ls／mkdir／rmdir／cp／mv／rm 负责目录与文件的组织；cat／tac／more／head／tail／grep 负责文本查看与检索；touch／chown 负责时间戳与属主权限；find 负责按名字搜索；tar 负责打包压缩。Linux 的权限模型为“属主／属组／其他人”各三位（rwx），因此写 /、/usr 这类系统目录以及执行 chown root 都需要 root 身份。

3.2 HDFS 与 Hadoop 基本操作

HDFS 采用 Master/Slave 架构：NameNode 保存整个文件系统的命名空间与元数据（文件—数据块的映射、权限、副本位置），DataNode 保存真实的数据块。客户端读写时先访问 NameNode 取得元数据，再直接与 DataNode 交换数据流；YARN 的 ResourceManager／NodeManager 负责为 MapReduce 作业分配容器资源。HDFS 提供了两套等价接口：命令行 hdfs dfs … 与 Java API（org.apache.hadoop.fs.FileSystem），后者是前者的底层实现。

3.3 MapReduce 编程模型

MapReduce 把计算抽象为 Map（把输入解析成 <key, value>）与 Reduce（对相同 key 的 value 集合做归并）两个阶段，框架在两者之间自动完成 分区、排序、合并、洗牌（Shuffle）。本实验三个题目正是利用“框架会对 key 排序、相同 key 会进入同一次 reduce 调用”这两个特性来实现：

  • 合并去重：以“整行内容”为 key，reduce 中每个 key 只输出一次，重复行自然消失，输出同时按行有序。
  • 排序并编号：以整数本身为 key，框架排序后 reduce 收到升序 key；再用 1 个 Reduce 任务 + 计数器即可产生全局连续位次。
  • 祖孙关系挖掘：一趟 MapReduce 完成自连接——每行 (child, parent) 发出两条记录，以“中间人”为 key 聚齐其子辈与父辈，reduce 中做笛卡尔积得到 (孙辈, 祖辈)。

五、结论分析与体会

  1. 三类操作的关系弄清楚了。Linux 命令负责“操作系统层面”的资源管理，Hadoop Shell 负责“集群层面”的操作，而 Java API 与 Shell 命令本质是同一套 HDFS 客户端的不同封装——实验中 Shell 与 Java 两个实现跑同一场景，输出逐条一致，这一点体会最深。
  2. MapReduce 的核心是“把问题翻译成 key”。三个题目代码量都不大，难点在 key 的设计：以整行为 key 得到去重，以整数为 key 借框架排序，以中间人为 key 完成自连接。理解了“框架对 key 排序、相同 key 进同一次 reduce”这两条，就能把很多看似不同的问题统一处理。
  3. Shell 与 Java API 并非完全等价，踩到了 3 个差异：① hdfs dfs -put 不会自动创建父目录，而 Java 的 copyFromLocalFile 内部会 mkdirs；② hdfs dfs -count 输出的“目录数”包含目录自身，用 0 判空会误判，而 Java 的 listStatus().length==0 没有这个坑；③ HDFS 的 append 只能追加到末尾，Java API 里直接调 fs.append，Shell 里用 -appendToFile，两者都无法“追加到开头”，必须整体重写。这些差异提醒我：写代码时不能想当然地认为命令行与 API 行为一致，要以实测为准。
  4. 环境问题往往比算法更费时间。本实验仓库路径中包含中文（“文档”），最初提交 MapReduce 作业时容器直接启动失败。通过查看 container-launch 诊断日志，发现路径里的中文被 JVM 转成了 ??????，容器因此无法创建日志目录；最终在 yarn-site.xml 的环境变量白名单中加入 LANG/LC_ALL/LANGUAGE，并在 mapred-site.xml 里为容器 JVM 显式指定 -Dfile.encoding=UTF-8 -Dsun.jnu.encoding=UTF-8 后问题解决。过程虽然曲折，但让我真正理解了 YARN 容器环境是“被裁剪过的”，以及 locale/编码对分布式程序的影响。
  5. 工程习惯上的收获。把每一步都落盘成日志、把标准答案放进 expected/ 并用 diff 自动校验、把所有实验目录、配置与启动脚本都脚本化，使整个实验可以一键复现；代码按题目拆分成独立类并配统一 CLI，也便于后续实验复用。

六、问答题（就实验中遇到的问题自拟）

问 1：执行 rmdir -p /tmp/a1/a2/a3/a4 时，为什么最后会报“删除目录 '/tmp' 失败：设备或资源忙”？

答：rmdir -p 的语义不只是删除给定目录，而是“删除该目录，并继续向上删除已经变空的各级父目录”。本例中 a4→a3→a2→a1 被依次删除后，/tmp 恰好变成空目录，于是 rmdir 继续尝试删除 /tmp 本身；但真实 Linux 上 /tmp 是一个挂载点（通常由 systemd 挂成 tmpfs），而挂载点被内核视为“正在使用”，删除会返回 EBUSY，所以 rmdir 报“设备或资源忙”并停止，返回非 0 状态码。这不是配置错误，而是符合预期的保护行为：/ 也会被同样地拒绝删除。实验也验证了这一点——把 /tmp 也做成挂载点后，各题行为与真实系统完全一致；反之若 /tmp 只是普通目录，rmdir -p 会把它一起删掉，从而连累后面所有涉及 /tmp 的题目。

问 2：题目 8 要求“追加内容到原有文件的开头”，为什么不能直接调用 HDFS 的 append？最后是怎么实现的？

答：HDFS 的文件在存储层面由一系列数据块顺序组成，客户端写入时会先向 NameNode 申请租约（lease）并追加到最后一个数据块的末尾，因此 FileSystem.append() 与 hdfs dfs -appendToFile 在设计上就只支持“末尾追加”，HDFS 没有提供“在文件头部插入”的接口——这既符合 HDFS “一次写入、多次读取”的定位，也避免了插入导致所有块编号与副本位置重排的巨大开销。实验中只能采取“整体重写”的思路：先把原文件内容完整读出，再删除原文件、重新创建，并按“新内容 + 原内容”的顺序写入（Java 实现为 fs.open 读出 → fs.delete → fs.create 写出；Shell 实现为 -get → 本地重组 → -rm → -put）。实测追加前 120 字符、追加后 168 字符，内容与顺序均正确。需要注意的是这种做法对超大文件代价很高，实际生产中若要频繁在头部插入，应改用 HBase 等适合随机写的存储。

问 3：提交 MapReduce 作业时容器报 “Exception from container-launch” 并失败，如何定位和解决？

答：定位过程分三步：① 客户端只报“Failing the application”，信息不足，于是到 YARN 的作业页面与 NodeManager 日志中查看 container-launch 的具体诊断；② 诊断日志里出现 log4j:ERROR setFile(null,true) call failed，路径被打印成 /home/yxy/??????/deepseek-harness/…，看到 6 个问号立刻意识到是中文目录名“文档”无法编码；③ 进一步确认原因是容器 JVM 的 locale 为 ASCII（容器环境变量经过白名单裁剪，LANG 没有传进去），JVM 用 ASCII 解析文件名时把不可表示的字符替换成 ?，导致容器创建日志目录失败、启动脚本异常退出。解决办法是在 yarn-site.xml 的 yarn.nodemanager.env-whitelist 中补上 LANG,LC_ALL,LANGUAGE（让容器继承 UTF-8 的 locale），并在 mapred-site.xml 中用 yarn.app.mapreduce.am.command-opts、mapreduce.map.java.opts、mapreduce.reduce.java.opts 为容器 JVM 显式加上 -Dfile.encoding=UTF-8 -Dsun.jnu.encoding=UTF-8。重启集群后三个作业全部一次通过。这个问题的教训是：把工程放在非 ASCII 路径下、以及容器环境变量被裁剪，都会引发很隐蔽的故障，排查时应优先看守护进程与容器的原始日志，而不是只看客户端的报错。
